# The WATCH'S OWN STROKE COUNTER for the rows in
# scripts/fixtures/lock_snap_records.txt -- the SAME records, in the same
# order, line for line. Read by scripts/lock_snap_replay.py, which requires
# that alignment and refuses to publish a figure if the files have drifted
# apart.
#
# WHY THIS FILE EXISTS. #196's first round graded every selectivity figure
# against a 31 s centred median of `rate_raw` and said in the harness that this
# was "the strongest [truth] available". It was not, and the stronger one was
# in these same three recordings all along: the FIT NATIVE `cadence` field is
# produced by a SECOND DETECTOR. StrongRow is a watch-app (manifest.xml) that
# READS ai.currentCadence (source/StrongRowView.mc:5445-5449) and writes no
# native record field, so this series is independent of BOTH candidates the
# snap chooses between -- the median-of-periods and the autocorrelation lock.
# A truth derived from `rate_raw` cannot referee a dispute in which `rate_raw`
# is one of the two parties; this one can.
#
# FORMAT
#   ROW <key> <label>                     starts a row; same keys, same order
#   CAD <cadence>                         one recorded second, integer spm
#   LAP <index> <step> <cycles> <seconds> one lap message, after that row's CAD
#                                         lines
#   Lines beginning with # and blank lines are ignored.
#
# PROVENANCE, so this is reproducible from the originals with any FIT decoder:
#   source files   i183553852.fit, i178249719.fit, i174014735.fit
#   CAD values     the NATIVE `cadence` field (number 4) of record messages
#                  (FIT global message 20), in timestamp order
#   selection      the SAME records lock_snap_records.txt carries, by the same
#                  rule (a record is written only if it carries all four replay
#                  fields), so the three files are line-for-line aligned
#   LAP values     lap messages (FIT global 19): message_index (254),
#                  lap_step_type (developer field id 25), total_cycles (10) and
#                  total_elapsed_time (7)
#   precision      `cadence` is a UINT8 in spm and is written unrounded. It is
#                  an INTEGER on every record of all three rows -- 8663 of 8663
#                  -- and `fractional_cadence` (number 53) is 0.0 on every one
#                  of them, so no resolution is lost by omitting it. Measured,
#                  not assumed.
#
# ABSENCE IS `-`, AND 0 IS NOT ABSENCE.
#
#   CAD  no record of any of the three rows is MISSING `cadence`, so no `-`
#        appears in a CAD line. A 0 IS A REAL READING: it is the counter
#        saying it is not counting, and 1777 / 1268 / 401 records carry
#        exactly that. It is NOT usable as a witness -- a counter reading zero
#        cannot say which of two non-zero candidates is right -- so
#        lock_snap_replay.py SKIPS those records when scoring and reports how
#        many it skipped. Treating a 0 as "0 spm was rowed" would be absence
#        rendered as a value, which is a named defect class here.
#
#   LAP  `lap_step_type` is `-` on ALL 17 laps of i178249719 and ALL 5 of
#        i174014735: both rows predate developer field 25. i183553852 carries
#        it on all 17.
#
# WHAT THIS WITNESS IS NOT. It is not unbiased in LEVEL. This repository has
# already measured that the native counter counts BLADE MOVEMENTS, not drives
# -- "89-109 blade movements against 66-68 drives"
# (source/StrongRowView.mc:710-712), which is the measurement correctiveRate()
# is built on. So it is used as a RATIO-SCALE witness: one scalar per row,
# k = median(cadence / rate_raw) over the records where the snap does not fire,
# and every conclusion is swept over k +-25%. A level error cannot flip a
# comparison between two candidates a factor of two or three apart unless it
# moves the witness across their GEOMETRIC MEAN, which is why the comparison
# is made in ratio space and not in absolute spm.
#
# Its independence is at the ALGORITHM level only: it shares the same wrist and
# the same accelerometer. Which firmware component produces it is not
# established here, and cannot be from a decoded file.
#
# CROSS-CHECKS a reader can run against the originals, all pinned by
# scripts/test_lock_snap_replay.py:
#   records written        3385, 3002, 2276 -- identical to the companions
#   cadence non-zero on    1608, 1734, 1875 records

#                          1.077, 1.303, 0.988

#                          That is the COOL-DOWN lap the branch's motivating
#                          sequence (records 2489-2505) sits in, and 6.49 spm
#                          is what makes the lock's 6.383 the better of the two
#                          candidates there rather than the worse.
#   i183553852             cadence reads 0 for the 187 consecutive records from
#                          2488 through 2674; the first non-zero after it is
#                          record 2675, at 10 spm.
